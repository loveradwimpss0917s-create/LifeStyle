## 1. Executive Summary

**HIBISTACKは「土台は完成しているのに、看板に名前も顔も書いていない店」である。**

技術基盤・アクセシビリティ・モーション設計は、個人メディアとしては明確に上位にある。
実測でアクセシビリティ100点、CLS 0、全14ページで横スクロール破綻ゼロ、
`prefers-reduced-motion`対応が13ファイル。これは「作れていない」サイトではない。

問題は**別のところにある**。

1. トップページで「誰が」「何を根拠に」書いているのかが一切分からない
2. 記事ページに**著者名が1文字も表示されていない**(実測: 本文中の出現0回)
3. トップページの最新記事が**構造的に必ず2回表示される**バグがある
4. 商品ページの自動比較表が、タオルケットとカセットコンロと椅子を比較している

つまり、**このサイトの弱点はUIの装飾不足ではなく、「信頼の可視化」と「重複の整理」**である。
そして今回の最重要論点である「もっと動的にすべきか」への答えは——

**すでに十分動いている。足すのではなく、壊れているものを直すべき段階。**

## 4. UI/UX詳細評価

### 4-1. 第一印象(モバイル390×844で実測)

ファーストビューに表示される情報:
`HIBISTACK`ロゴ / ハート・検索・メニューアイコン / ヒーロー写真(喫茶店のコーヒー) /
`HIBISTACK — Life & Living` / `日々の暮らしを、少しだけ豊かにする。`

| 3秒で分かるか | 判定 | 根拠 |
|---|---|---|
| 何のサイトか | **✕** | 「Life & Living」「暮らしを豊かに」はムード表現であり、レビューサイトだと分からない |
| 誰が運営しているか | **✕** | 人物情報がファーストビューに一切ない |
| 何を読むサイトか | **△** | スクロールして「Journal」まで到達すれば分かる(551px地点) |
| なぜここを見るか | **✕** | 「実際に買って使った」という唯一の差別化要因が画面上にない |

**最重要の発見**: `<title>`タグは
`HIBISTACK | 実際に買って使った、正直な暮らしのレビュー`
という**極めて優れたポジショニング文**を持っている。
しかしこの一文は**ページ本文には一度も表示されない**。
サイト最良のコピーが、検索結果とブラウザタブにしか存在しない。

### 4-2. トップページの構造的欠陥(コードで根本原因を特定)

`src/pages/index.astro`:

```js
const latestArticles = articles.slice(0, 3);  // Journal に articles[0..2]
const featured = articles[0];                  // Editor's Picks に articles[0] を再掲
```

`featured`は`latestArticles[0]`と**常に同一**。よって
**最新記事は必ずトップページに2回表示される**。データではなく構造の問題であり、
今後どの記事を公開しても永続的に発生する。

実測(リンク解析):

| セクション | 内容 |
|---|---|
| Journal | JSF記事 / コンビ記事 / イワタニ記事 |
| Editor's Picks | **JSF記事(再掲)** / 北欧チェア |
| Best Picks | JSF商品+**JSF記事(3回目)** / コンビ×3 / イワタニ+**記事(2回目)** |

- ホームページ総リンク14本 → **ユニークは10本のみ**
- JSF記事は**3回**、他2記事は**2回**登場
- ページ高さ**8,797px = モバイル10.4画面分**。ユニーク1件あたり約840pxのスクロール

### 4-3. Editor's Picksのレイアウト崩れ(デスクトップ1440pxで実測)

```
gridTemplateColumns: "247.203px 247.203px 247.203px 247.203px"  ← 4カラム
itemCount: 1                                                     ← 中身1件
gridWidth: 1085px
```

`site.json`の`editorsPicks`は`["nordic-paper-cord-dining-chair"]`の**1件のみ**だが、
`<ProductGrid columns={4}>`で描画されるため、
**247pxのカード1枚に対し838pxの空白**が右に広がる。実画面で確認済み。
「未完成のサイト」に見える最大の視覚的要因。

さらに「編集部のおすすめ」という見出しの中身が
**時系列で決まる最新記事**である点は、名実の不一致。

### 4-4. 商品ページの自動比較表(実画面で確認)

JSF TOWELKET(タオルケット・¥11,000)のページに表示される「同じカテゴリで比較」:

| | JSF TOWELKET | イワタニ 炙りや2 | 北欧ペーパーコードチェア |
|---|---|---|---|
| おすすめ度 | ★5 | ★5 | ★4 |
| 参考価格 | ¥11,000 | — | ¥16,919 |
| 使用期間 | 1ヶ月未満 | 1ヶ月未満 | 1ヶ月未満 |

**タオルケットとカセットガス炉端焼き器と椅子を、価格と星の数で比較している。**
`category: living`が広すぎるため、比較として意味を成していない。
購入判断に寄与しないどころか、サイトの判断力への信頼を損なう。

### 4-5. E-E-A-T: 著者の不在(実測)

記事本文(`<main>`内)における出現回数:

| 語 | 出現 |
|---|---|
| きのこ | **0回** |
| HIBISTACK | **0回** |
| 著者 / 執筆 | **0回** |

JSON-LDは`"author":{"@id":".../about/#person"}`と**構造的には正しい**。
しかし**人間の読者には著者が一切見えない**。

「実際に買って使った、正直なレビュー」を掲げるサイトで、
書き手が匿名であることは、E-E-A-Tにおける最大の機会損失。
Googleのレビューシステム評価基準は「一次体験の証拠」と「誰が語っているか」を明示的に重視する。

| 観点 | 判定 | 実測根拠 |
|---|---|---|
| 視覚的階層 | ○ | 見出し32px / 本文17px / メタ12-14px の明確な3層 |
| タッチターゲット | △ | FavoriteButtonは44px確保(ヒットテストで実証)。ただし後述の例外あり |

**タッチターゲットの実測例外**:
`.ranking-item__article-link`(「使ってみた感想を読む」)は

ランキングページに**6箇所以上**出現する。

### 4-7. 「静かすぎる」問題の判定

提示された4分類のうち、**単一では該当しない**。ページごとに異なる:

| ページ | 判定 |
|---|---|
| 記事ページ | **ブランドとして意図的なミニマリズム**。写真・余白・17px/1.9行間の可読性は完成している |
| 商品ページ | **情報量不足でサイトが未完成に見える**。本文平均432字は「静か」ではなく「空」 |
| トップページ | **シンプルだが少し寂しい**。正確には「寂しい」のではなく**同じものが3回出るので薄く見える** |
| カテゴリ/一覧 | **静かで上質** |

つまり「静かすぎる」のではなく、**濃度のムラ**が問題。
装飾を足すのではなく、**重複を削り、薄い場所に中身を入れる**のが正しい処方箋。

### 5-2. 3案の比較

| 案 | 評価 |
|---|---|
| **A: 現在の静的ミニマルUIを維持** | ✕ **前提が誤り**。現状はすでに「静的」ではない。この案は「何もしない」と同義で、上記の構造バグを放置する |
| **B: ミニマルUIを維持しつつ必要な場所だけ微細な動きを追加** | ◎ **採用**。ただし「追加」の中身は装飾ではなく、後述の通り**重複削除・情報密度の改善**が主 |
| **C: よりインタラクティブなメディアへ進化** | ✕ 記事8本・商品10点でインタラクションを増やすと、**中身の薄さが露呈するだけ**。カルーセルは「横に並べるものがある」場合にのみ機能する |

### 5-3. 結論

# B — ただし「動きを足す」フェーズではない

HIBISTACKは**すでにBの状態にある**。モーション設計はこの規模のサイトとして過剰なほど整っている
(reduced-motion 13ファイルは大手メディアでも珍しい)。

いま`transition`を1行増やしても、
「JSF TOWELKETの同じ写真が3回出てくる」問題も
「誰が書いたか分からない」問題も何ひとつ解決しない。

**やるべきは、動きの追加ではなく「重複の削除」と「信頼の可視化」。**
その上で、既存モーションの**チューニング**(下記P0-5、P1-2)だけを行う。

## 6. 今すぐ変更すべきUI TOP10

具体的な実装内容まで記述する(抽象論は禁止のため)。

### P0(今すぐ・すべてコード変更のみで完結)

> **✅ P0-1〜P0-5は2026-08-26に実装・実測検証済み。** 各項目末尾に検証結果を追記した。

**P0-1. トップページの記事重複を解消**
`index.astro`の`const featured = articles[0]`を`articles[3]`(Journalの3本に含まれない次点)へ変更、
または`latestArticles`を`articles.slice(1, 4)`にずらす。
後者を推奨(「Editor's Picks=最新の目玉」という意味が保たれるため)。
→ ユニーク10件が10件のまま、重複3回→0回。
**✅ 実装済み**: `articles[latestArticles.length]`を採用。実測で`featured`は`/articles/aeropress-go-review/`となり
Journalの3本と重複なし(`featuredIsDuplicateOfJournal: false`)。孤立記事だったAeroPress記事が導線に乗る副次効果もあった。

**P0-2. Editor's Picksの空白カラムを解消**
`<ProductGrid items={editorsPicks} columns={4}>`を
`columns={Math.min(editorsPicks.length, 4)}`に変更。
1件なら1カラム(=幅いっぱいの大きなカード)になり、838pxの空白が消える。
あわせて`site.json`の`editorsPicks`を3〜4件に増やす(オーナー作業)。
**✅ 実装済み**: 実測でグリッドが`4×247px`→`2×526px`に変化。カードは247px→526pxとなり空白は838px→526pxへ。
ただし1件のままでは半分が空くため、**完全な解決にはオーナーによるピック追加が必要**。

**P0-3. 記事ページに著者バイラインを追加**
`ArticleLayout.astro`の日付の隣に、`site.json`の`author`から
丸型アバター(32px)+「きのこ」+`/about/`へのリンクを配置。
JSON-LDの`Person`と視覚表現が一致し、E-E-A-Tの穴が塞がる。
**投資対効果が最も高い1件。**
**✅ 実装済み**: 「きのこ / 実際に買って使った人」+丸型アバターを`/about/`リンク付きで表示(実測172×44px、タップ高さ44px確保)。
あわせてオーナー確認のうえ`site.json`の`author.name`を`HIBISTACK`→`きのこ`に変更し、
Person構造化データが「サイト名と同名の人物」になっていた不整合も解消した。

**P0-4. トップページに1行のポジショニング文を追加**

## 7. 今は変更しないUI(やらないことリスト)

## 8. 技術面の評価(§17対応)

| 指標 | 実測値 | 評価 |
|---|---|---|
| LCP(記事) | 3.6s | △ 要改善域(2.5s超) |
| CLS | **0** | ◎ |
| TBT(記事) | 380ms | △ |
| max-potential-FID | score 0.2 | ✕ INPの潜在リスク |
| JavaScript総量 | **16KB**(ClientRouterのみ) | ◎ 極めて軽量 |
| Script Evaluation | 58ms | ◎ |
| **Style & Layout** | **1,007ms(メインスレッド1.6秒の63%)** | ✕ **真のボトルネック** |
| 総転送量(記事) | 547KB | ○ |

**重要な所見**: 性能の足を引っ張っているのは**JavaScriptではなくStyle & Layout**。
JSはわずか16KBで実行58msに過ぎない。

原因の有力候補は`astro.config.mjs`の`inlineStylesheets: 'always'`:

| ページ | HTML全体 | うちインラインCSS |
|---|---|---|
| トップ | 103KB | **32KB(31%)** |
| 記事 | 101KB | **35KB(34%)** |
| 商品 | 112KB | **42KB(37%)** |

同じCSSが全ページに複製され、**キャッシュが一切効かない**。
View Transitionsで記事を渡り歩くたびに35KBのCSSを再取得・再パースしている。

ただしこれは「レンダーブロッキングを避ける」という**意図的な選択**であり(コメントに経緯あり)、
外部化すればCSSは1回のキャッシュで済む一方、初回はリクエストが1本増える。
**A/B両方をLighthouseで実測してから決めるべき**であり、今回は「要検証」に留める。

**やってはいけないこと**: この状態でアニメーションを増やすと、
Style & Layoutコストが直撃で増える。動的化を見送る技術的根拠でもある。

## 12. 最終提言 — AppleとメディアのバランスをどこでとるかHIBISTACKにおける最適解は、

**「構造はApple、中身は雑誌」**

である。

- **構造(骨格)= Apple的**: 一貫したトークン、予測可能な操作、44pxのタップ領域、
  reduced-motion対応、CLS 0。ここは既に達成しており、**今後も動かさない**。
- **中身(肉)= 雑誌的**: 写真の大きさ、実体験の density、書き手の顔、
  「この人がこう感じた」という一次情報。**ここが決定的に足りていない。**

雑誌が読まれるのは、動くからではなく**中身が濃く、書き手が信頼できるから**。
HIBISTACKに足りないのは`transition`ではなく、**バイライン1つと本文800字**である。

いま「動的にすべきか」と問うのは、
既に整った器に、さらに装飾を足そうとしている状態にあたる。
**器は完成している。次に必要なのは、器に見合う中身と、作り手の名前。**
